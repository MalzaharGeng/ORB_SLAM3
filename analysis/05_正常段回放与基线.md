# 05 · 事故前"正常段"回放与基线对比

补做时间：2026-11-06 00:2x（对 2026-11-05 夜航 `Tm7tjC`）
对照组：`04` 之前的事故段回放（`event_1603810252_3003_6`，1352.87–1372.81 s）

## 1. 为什么补做这一段

上一轮只回放了 **事故段**（`airborne_fault_latched` 触发的那 20 s）。缺一个"同一架飞机、同一次上电、同一个 VIO 进程，但在一切正常时"的对照。没有对照，无法回答"VIO 到底行不行"——只能看到坏的那一段。

本次把 `Tm7tjC` 这次运行里 **事故前被滚动录制下来的 6 段**（284.15–411.82 s，共 127.7 s）全部找出来，分两组回放：

- **N0**：只回放 `3003_0`（284.15–304.13 s）。这是第一段，触发原因是 `time_sync_unready`，但它在时间上位于门控锁存（305.2 s）**之前**，飞行状态是悬停，因此是能拿到的最干净的一段。
- **NA**：把 `3003_0 … 3003_5` 六段按时间拼成一条 127.7 s 的连续输入回放，用来观察从"正常悬停"过渡到"门控锁存、PX4 降级"的整个过程。

## 2. 回放方法

### 2.1 单段

`RollingInputRecording` 的 event 目录 → `stereo.csv` + 根 `imu.csv`（index 从 0 重排）。

⚠️ 沿用 04 的修正：`RollingInputRecording.cc:159` 写入顺序是 **`t, ax, ay, az, gx, gy, gz`（加速度在前）**。按"角速度在前"转换会得到 |a|≈1.2 m/s²、|ω|≈490 °/s 的垃圾数据。

### 2.2 拼接（NA）

新写 `scripts/replay_splice_rolling.py`，规则：

1. 六个事件的帧按图像时间戳全局排序；
2. 相邻帧间隔 < 半帧周期（约 33 ms）视为重叠，只保留一帧；
3. 被丢弃帧携带的 IMU 样本**补进前一个保留帧**（按时间戳去重），避免重叠区出现 IMU 空洞；
4. 每帧的 IMU 批只保留严格晚于前一帧末样本的部分，保证全局单调；
5. index 从 0 连续重排。

结果：285+293+284+279+280+247 = 1668 帧 → **1091 帧**（去重 577 帧），跨度 127.67 s，与六段原始跨度（284.15→411.82 = 127.67 s）完全一致。

> 局限（必读）：`3003_2` 结束于 323.33 s，`3003_3` 从 370.89 s 开始，中间 **47.5 s 没有任何录制**。拼接后这段是时间跳变，回放器会打印 `Timestamp jump detected. State set to LOST` 并强制重建地图。因此 NA 的**位置轨迹在 322 s / 370 s / 409 s 处不连续**，不能拿来做长距离精度评估；它只适合评估"跟踪与初始化的健康度"。

### 3.2 关键观察一：悬停段反而"初始化不了"

N0 的日志：

```
frame 150 (t=295.0) tracking=2
Not enough motion for initializing. Reseting...
TRACK: Reset map because local mapper set the bad imu flag
First KF:31; Map init KF:11
start VIBA 1 (mTinit=3.3995 s, threshold=3 s)
end VIBA 1
RECORDING_REPLAY_COMPLETE frames=285 valid_poses=269
```

- 视觉跟踪从未丢失（`tracking=OK` 99.6 %，0 次 LOST）；
- 但 **IMU 初始化被"运动不足"打断 2 次、地图重建 3 次，VIBA2 一次都没走到**；
- 最后 20 s 结束时，`ba2` 仍然是 0。

DX 对照：事故段（飞机在动）**11.0 s** 就完成 VIBA2，`valid` 99.7 %。NA 段（同类数据但后面还接着更多帧）在 **18.93 s** 才完成——正好卡在 N0 的 20 s 末尾。

**结论：VI-SLAM 的惯性初始化需要运动激励。纯悬停冷启动时，视觉能跟住，但尺度/重力方向定不下来，VIBA2 不完成。** 这不是"VIO 坏了"，是 ORB_SLAM3 IMU 初始化的固有前提，也是本项目门控设计里没有考虑的一类状态。

必须说清 replay 的局限：真实运行时 VIO 是**连续跑了 137 s** 才进入 284 s 的，不是冷启动；所以 N0 不能证明"当时 VIO 状态差"。它证明的是**能力边界**：一旦 VIO 被重置或需要重新初始化，而飞机正好在悬停，20 s 内恢复不了。

### 3.3 关键观察二：门控锁存时刻，VIO 输出完全正常

305.2 s（遥测里 `ev_pos` 由 1 变 0、`sent` 冻结在 2186 的那一帧）前后，VIO 侧**没有出现任何异常**：`valid` 一直是 1、`tracking` 一直是 OK、`ba2` 一直是 1、位置连续无跳变。

**这是"卡死不在 VIO 输出侧"的最直接证据**：门控判定 `time_sync_unready` 的那一刻，VIO 送出来的位姿是健康的。卡的是程序自己做的时间同步合法性判定（系统时间停在 1970 → `vio-clock-prepare` 因 RTC 年份无效跳过自愈）。

### 3.4 关键观察三：正常段的漂移速率

NA 中 303.0 → 312.0 s（9 s，飞机悬停，PX4 `ekf` 位置基本不动）：

- VIO 位移 **0.70 m / 8.9 s = 0.079 m/s**
- 同期 PX4 `ekf` 位置从 (3.04, −0.01, 0.85) 到 (3.51, 0.37, 0.74)，约 0.5 m

两者同量级、同方向（都在 +y 方向小幅移动），但 VIO 的 +y 分量更大（1.39 m @ 322 s vs PX4 0.37 m）。**室内悬停时的 VIO 水平漂移量级约 5–8 cm/s**，一分钟后约 3–5 m。这个量级远小于"漂 102 m"——102 m 是 305.2 s 之后 PX4 失去 EV 更新、纯 IMU 积分 100 s 的结果，与 VIO 精度无关。

### 3.5 观察四：拼接段的耗时与实机的差别

`track_ms`（TrackStereo 实际调用耗时，含锁等待）三组都是 51–54 ms（p50），p95 55–62 ms，对比帧间隔 66.7 ms：

- 单帧跟踪能塞进帧周期，但余量只有 4–15 ms；
- `cycle_ms`（含 PNG 解码 read）p50 66.8 ms，与帧周期持平 → 回放时靠"刚好跟上"运行，偶尔（1.8–2.7 % 帧）超时；
- 实机没有 PNG 解码开销（`read_ms` 14 ms 是回放器特有），实机 `cycle` 会更低；但 `track_ms` 本身已吃掉 77–80 % 的帧预算，这解释了现场 `track_ms 40~77 ms` 与 `observation_gap` 的出现。

## 4. 结论（可直接引用的四条）

1. **VIO 输出侧在正常段与故障时刻都是健康的**：`tracking=OK` 99.6–99.9 %，0 次 LOST；305.2 s 门控锁存的那一帧前后 VIO 位姿连续、`ba2=1`、无跳变。事故的起点在程序侧的时间同步判定，不在 SLAM。
2. **纯悬停冷启动是 VIO 的真实弱点**：运动不足导致 IMU 初始化反复回退，20 s 内 VIBA2 完不成（N0：0 %）；一旦有运动激励（事故段），11 s 就能完成。这解释了"有时能飞、有时一上电就废"的随机性，也说明门控的 `stable_seconds=1.0` 与 `max_age=0.25` 这类"短窗口"假设不成立于悬停场景。
3. **`time_sync_unready` 不是突发故障，而是从发布开始就持续存在的劣化**：284 s 之前 `rejected` 已累计 1961 次，六段录制里有五段的触发原因就是它。因此修复方向不是"抑制某一次误判"，而是修时钟（开机自愈校时）。
4. **漂移 102 m 与 VIO 精度无关**：VIO 在悬停段的水平漂移是 5–8 cm/s 量级；102 m 来自 305.2 s 锁存后 PX4 失去 EV 更新、纯 IMU 积分约 100 s。
