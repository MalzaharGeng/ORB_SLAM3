# 事故复盘：两次飞行的完整时间线

> 数据源：`data/flight_log/14_07_14.ulg` + `data/nanovio/Tm7tjC/`

结论先行：这一夜可复现的工程问题是 VIO 观测被门控拦截并永久锁存，另有一项设计缺陷放大了后果。

| 问题 | 性质 | 依据 |
|---|---|---|
| VIO 观测被门控拦截（RTT 20,387 us / 样本间隔 1.067747 s 越过旧门限） | 软件/配置 | `px4_telemetry.csv` 逐帧判据，统计见 `../repair-20261106/analysis.json` |
| 故障锁存无降级路径（单帧异常即判死整场） | 设计缺陷 | `../repair-20261106/baseline/src/Px4Vio.cc` 与 `run.log` 锁存段 |

> 修订（2026-11-06）：旧版把「时钟 1970」写为根因。`../repair-20261106/复盘与修复报告.md` 核实门控比较的是 RTT、相对偏差和新鲜度，年份不正确不等于一定触发这些条件；1970 需要修，但直接因果关系未被证明。DDS TIMESYNC 的偏差也不能直接推算真实 UTC。

> **低电压告警标注（2026-11-06）**：第二次飞行的 `battery_status.warning` 于 5.7 s 起置位、6.7 s 达 3，但 `COM_LOW_BAT_ACT=0` 未触发任何飞控动作；迫降段下降与遥控油门一致。该告警是**伴随遥测记录，对本次事故没有影响**，不列为故障或原因。电压数据保留在第三节与 `repair-20261106/final_flight_timeline.json`，证据边界见 `analysis/07_修复与复盘.md`。

> 修订（2026-11-06，证据边界，见 07）：重放证明的是**被记录窗口内可跟踪**，不能证明整场无漂移或实时闭环安全。重算显示 286 帧里 285 帧正常跟踪、拼接 127.7 秒数据 tracking 一次都没丢——到此为止。

## 二、第一次飞行：漂移 102 米（t = 126 ~ 412 s，286 秒）

### 时间线

| t (s) | 事件 | 状态 |
|---|---|---|
| 126.1 | 解锁 | `armed=1`，`px4_local_frame_unready` |
| 135~145 | 手摇初始化 | `inertial_initializing`，高度 −1.48 m（原点在手上） |
| **147.5** | **VIO 开始发布** | `publishing`，`EV=1/1`，dH 0.05 |
| 165.7 | 切 POSCTL | `mode` 1→2 |
| 165~214 | 定点悬停 | x 2.5、y −0.1，**dH 0.00~0.15**，稳 |
| 214~228 | 真实机动 | vx 到 1.26 m/s，2 秒移动 2 m（物理合理，**不是跳变**） |
| 228~305 | VIO 帧率走低 | `reason` 多为 `waiting_new_frame`；同期 `rejected` 已累计 **1961 次** |
| **305.2** | **永久锁存** | `time_sync_unready` → `observation_gap` → `airborne_fault_latched` |
| 308.2 | **降级 ALTCTL** | PX4 主动放弃定点（位置失效） |
| 308~412 | **漂移** | y 从 −0.01 涨到 98.79 |
| 368.5 | EKF 二次崩 | 单帧 x=7.69 → **−28.20**（2 秒 36 m，物理不可能） |
| 412.9 | 上锁 | 位置 (−19.24, **102.25**) |

### 锁存瞬间的原始日志

```
[PX4] publishing        hz=14.96  sent=2176  EV=1/1/0     ← 一直正常
[PX4] time_sync_unready hz=14.99  sent=2186  EV=1/1/0     ← 时钟判定失效
[PX4] time_sync_unready hz=0.999  sent=2186  EV=0/0/0
[PX4] observation_gap   hz=0.999  sent=2186  EV=0/0/0     ← 观测间隔超限
[PX4] airborne_fault_latched      sent=2186               ← 锁存，sent 冻结
```

`sent` 从 2176 停在 2186，之后 `rejected` 一路涨到 1990。**VIO 从此一帧都发不出去。**

**补做证据（见 `05_正常段回放与基线.md`）**：用同一批图像离线重跑，305.2 s 前后逐帧 `valid=1 / tracking=OK / ba2=1`，位置从 (−0.01, −0.02, 0.05) 到 (−0.02, −0.02, 0.05)，连续无跳变。也就是说：**门控判死它的那一刻，它送出来的位姿是好的。** 问题在时钟判定，不在位姿本身。

### 因果链

```
遥测首行零点后 303.217721 s：RTT 20,387 us 越过 20 ms 门限
  → time_sync_unready（VIO 算出位姿但拒发）
304.223915 s：同步质量已恢复，样本间隔 1.067747 s 越过 0.30 s 门限
  → observation_gap
304.229503 s：airborne_fault_latched，sent 冻结在 2186（本次解锁期间不再恢复）
  → PX4 失去视觉位置，POSCTL → ALTCTL
  → ALTCTL 无水平位置保持，摇杆只能控姿态
  → 漂移 102 m
```

上述秒数以 `px4_telemetry.csv` 首行 `system_us=231943014` 为零，与本节时间线使用的会话时间轴不同，对照时不能直接混用。Nano 启动在 1970 年是待修的环境问题，但没有证据表明年份本身触发了上述 RTT / 间隔判据（见 `../repair-20261106/复盘与修复报告.md`）。

### 控制链正常

```
飞行全程 t=2.35 ~ t=40.55：
  torque_setpoint_achieved = 1     ✓
  thrust_setpoint_achieved = 1     ✓
  actuator_saturation = [0,0,0,0]  ✓ 无饱和
```

`-2`（UNDERTORQUE）只在起飞前和落地后出现，**飞行中一次都没有**。

杆量、目标倾角与实际姿态的对应关系（5–40 s 整段拟合下，实际姿态约滞后 0.21 s）：

```
rc_roll=+0.40 → 实测 roll=+14.4°
rc_roll=−0.29 → 实测 roll=−11.2°
```

### 判断

飞机没有“飞出去”（位置只动 0.84 m），是在**原地剧烈摆动**。`rc` 杆在 ±0.3~0.5 之间来回，实测姿态 ±10~16°，属于人在追着修正的形态。

电机输出记录为 0.80~0.85，同时 ALTCTL 没有水平位置环，杆量请求的是目标倾角而非横向速度。已定位的「持续打杆仍朝反方向移动」片段符合先刹掉已有横向速度、再反向移动的过程；控制分配器未报告饱和，这些数据不支持据此断言「电机已饱和所以抢杆」。上述滞后是整段动态响应的近似拟合，包含控制器与机体动态，不是单独测出的通信延迟，也不能凭此判定控制器故障；位置、速度、姿态均为飞控估计，不构成对落地异常的完整根因结论（见 `../repair-20261106/最后一次飞行操控响应复核.md`）。

### 测试 C：事故前悬停段 `event_..._0`（284.15–304.13 s，285 帧）

| 指标 | 结果 |
|---|---|
| 有效位姿 | 269 / 285（94.4%） |
| tracking 分布 | `2`×284，`0`×1，**0 次 LOST** |

| IMU 初始化 | 被 `not enough motion` 打断 2 次，地图重建 3 次 |

**视觉能跟住，但惯性初始化定不下来。** 这是运动激励不足，不是算法错误 —— 详见 `05_正常段回放与基线.md`。

### 两次测试的差别说明什么

> **修订**：初版这里记录的是 105/286 与 43/1091，原因是格式转换时把 `imu.csv` 的加速度轴与角速度轴对调（`RollingInputRecording.cc:159` 的列序是 `t, ax, ay, az, gx, gy, gz`）。修正后几乎全程有效。

| 数据段 | 飞机动作 | 结果 |
|---|---|---|
| 284~412（拼接） | 悬停 + 被动漂移 | **1060/1091（97.2%），`tracking` 掉出 0 次** |
| 1352~1372（`_6`） | 手动大幅修正，动作激进 | **285/286（99.7%），全程正常** |
| 284~304（`_0` 单段） | 原地悬停 20 s | 269/285（94.4%），**VIBA2 未完成** |

在三组已记录的窗口内，重放均能稳定跟踪、跟踪丢失 0 次；第一次停发的直接触发点在 VIO → PX4 的门控判定。这只说明被记录窗口可以跟踪，不能证明整场无漂移、绝对精度正确或实时闭环必然安全；测试 C 的 BA2 全为 0，也不能把视觉 valid 直接当作可融合惯性导航。证据边界见 `../repair-20261106/复盘与修复报告.md`。

> 关于 `not enough acceleration`：它出现在 `run.log` 第 123~2188 行，即**初始化完成之前**。地面放置、电机不转时加速度恒为重力，初始化无法启动；一旦手摇（第 2194 行）35 行内即完成。空中机动段有姿态变化，能正常初始化（实验 A/B）。
>
> 补做实验 C 又划出一条边界：**空中原地静默悬停、只靠电机振动，同样会被判 `not enough motion`**，20 s 内 VIBA2 完不成。准确的说法是「需要足够的运动激励」，不是「需要离地」。

### 关于“拉不回来”的机制说明

| 场景 | 可核对的机制 |
|---|---|
| 第一次（漂移到 102 m） | ALTCTL 无位置保持，摇杆只能控姿态；另有 2 s 的 yaw 杆使航向变化约 76 deg，杆量对应的实际倾角约 6 deg |

这些位置、速度和姿态均来自飞控估计，不是外部真值；上述机制可以解释部分主观感受，不能据此断言已完整解释失控或落地异常，也不构成整次事故的根因结论。`COM_RC_OVERRIDE=3` 已生效，`manual_enabled=1` 全程，没有遥控器失效的证据。CPU 负载、同步抖动、VIO 估计误差是否参与最后一次操控异常，因果关系尚未建立（见 `../repair-20261106/最后一次飞行操控响应复核.md`）。
