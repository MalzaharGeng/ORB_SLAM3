## 一、仓库明文写了什么

### 提交和推送

[构建配置实施计划](plans/2026-11-08-build-profiles.md) 第 8 条原文：

> 代码、CI配置、文档分开提交，提交说明记录本地构建/测试数量及未验证边界。推送前 fetch 防止覆盖远端新增提交，普通 fast-forward 推送，回读引用与文件哈希。

同一计划的目标段写明两分支分别提交、不合并分支；结尾写明不删除数据集大文件或改写历史。
原文属于当轮构建工作的范围。本次整理中，维护者明确要求后续继续遵守这些提交、同步和历史保护方式。

据此执行：

- 代码、CI 配置、文档分别提交。没有 CI 变更时，不为了凑三次而创建空提交。仓库配置如忽略规则另作配置提交。
- 提交说明记录实际构建次数、测试数量和环境；没有运行的检查明确写“未验证”。
- 每次推送前 fetch；发现远端新增提交时先核实，不覆盖远端。普通 fast-forward 推送。
- 不对已发布历史执行 rebase -i、reset 后强推或其他历史重写；修正采用追加提交。
- 推送后重新获取远端引用，核对远端提交 ID 和改动文件的 SHA256。

## 四、忽略规则的实际效果

根 .gitignore 以三段规则起头：

~~~gitignore
*
!*.*
!*/
~~~

默认忽略无扩展名文件，重新放行带点名称的文件和目录；后续规则仍可再次忽略。
这不是“带扩展名就应该提交”：日志、录制、备份、二进制也可能带扩展名，仍须核查内容。
无扩展名脚本需要精确的 !完整路径 例外，并确保父目录可遍历；提交前可用：

~~~bash
git check-ignore -v path/to/new_file
git status --short --untracked-files=all
~~~

不要为加入脚本整体放行构建目录，也不要把 git add -f 当作长期忽略策略。
.gitignore 不会自动移除已跟踪文件；历史数据和资料不通过重写历史删除。

## 五、跨平台行尾

当前树中行尾混用。例如 CMakeLists.txt 是 LF，nano/README.md 是 CRLF。
本次核对的 core.autocrlf 未设置；不能依赖机器默认值推断原始 blob。

1. 修改前用 git show HEAD:path 读取原始字节，确认 CRLF / LF 和文件权限。
2. Windows/Linux 的语义核对可先剥回车；落盘时保留被改文件原有行尾。不要混用会转换行尾的工具。
3. 修改后检查 git diff --numstat。增删数接近整文件行数时，先排查行尾翻转。
4. git diff --check 用于检查新增空白错误。既有 CRLF 文件可能被当作行尾空白，需结合原始 blob 判读，不为消除提示而批量改全树。
5. 若确需统一行尾，单独说明、单独提交，保证归一化后内容不变。

## 六、一次改动的执行顺序

1. 读取本分支约定，确认目标长期线、环境、远端起点；设备工作目录有未提交内容时优先使用独立 worktree。
2. 保留原有行尾和权限，完成修改；源码与原始录制、备份、构建目录分开。
3. 在声明的环境执行适当构建和测试，记录数量与未验证范围。
4. 按代码、CI、文档或仓库配置拆分提交，使用中文事实说明。
5. fetch，核对目标引用仍是预期起点；普通 fast-forward 推送。
6. 回读远端引用与文件 SHA256，记录提交 ID 和校验结果。

性能目标：每目 1280×960、ORB 配置 1000 特征保持不变；评估 GPU 或并行实现时同时比较耗时、
关键点/描述子或匹配差异、回放跟踪质量。相机输入 60 fps 不等于 SLAM 实际处理 60 fps。
未接触实机期间使用已有录制、静态运行和故障注入；需要物理运动的边界明确留待验证。
