# DECXIN 的 GPU 处理后端

当前常驻入口已切换为校准后的 VIO，强制单缓冲和原取流时序；本文的双缓冲帧率属于纯双目优化对照。五米任务与首次空中初始化以 [部署流程](DECXIN_FIVE_METRE_FLIGHT.md) 为准。


## 处理边界

CUDA 是可选构建功能，当前提供 FAST-9 和双目立体校正两个独立开关。
默认 CPU 路径保持可用；不要求 OpenCV 编译 CUDA 图像模块。

本阶段保持相机 MJPEG 2720×960 @30、单 V4L2 缓冲，处理每目 960×720、
1000 配置特征、8 层金字塔、FAST 阈值 20/7。
校正先输出每目 1280×960，再由既有 Settings 缩放并同步内参和 bf。
外参、物理基线和图像时间戳生成位置不变。
完整原始状态内录、每帧导航和自动验证持续运行，日常图像编码仍关闭。

## 双目校正实现

CudaStereoRectifier 直接消费 CPU 原有的 CV_16SC2 坐标和 CV_16UC1 分数表，
使用 1/32 插值网格、相同整数舍入和相同零值边界。
图像越界以单目裁剪区域为准，不采样另一只镜头或填充区域。

校正表、显存和非阻塞流在每个采集线程内复用。
每帧只上传一次解码后的完整灰度图，再取回左右校正图。
原始输入可有行跨度，不要求连续内存。
本阶段仍需要回到 CPU 完成缩放、金字塔、方向、描述子和跟踪。

实例只属于一个采集或回放线程，初始化后表内容和几何必须保持不变。
检测到尺寸、裁剪或表身份改变，以及 CUDA 运行错误时，禁用该实例的 GPU 路径，
明确输出 CPU fallback，由调用者使用原有 cv::remap 重算整帧。

本实现追求与原输入字节一致，不通过改插值、裁视场、减少特征或修改标定换速度。
逐像素相等覆盖已验证输入，仍不能替代长期 VIO 和带真值的精度验证。

## 构建与运行

~~~bash
cmake -S . -B build -DORB_SLAM3_WITH_CUDA_FAST=ON \
  -DORB_SLAM3_CUDA_ARCH=87 -DORB_SLAM3_BUILD_TESTS=ON
cmake --build build --target stereo_uvc cuda_rectify_regression -j1

# 停止其他相机使用者后，临时选择 GPU 校正，FAST 仍由 CPU 执行
ORB_SLAM3_RECTIFY_BACKEND=cuda ORB_SLAM3_FAST_BACKEND=cpu \
VIO_PROCESSING_PROFILE=light ORB_SLAM3_PARALLEL_LEVELS=1 \
bash run_recovery_test.sh --headless --px4-config config/decxin_px4.yaml

# CPU 回退
ORB_SLAM3_RECTIFY_BACKEND=cpu bash run_recovery_test.sh --headless --check
~~~

构建开关沿用 ORB_SLAM3_WITH_CUDA_FAST，同时包含校正模块。
未构建 CUDA 的程序继续使用 CPU 路径。
effective_launcher.conf 记录两个后端选择；实际执行还应核对
run.log 中的 CUDA fixed-point remap active 或 CPU fallback。

## 回归入口

~~~bash
ctest --test-dir build -R '^cuda_rectify_regression$' --output-on-failure
build/tests/cuda_rectify_regression runtime_rectify.yaml motion_dataset 100000
~~~

无参数测试检查四组合成输入、全部 1024 种分数系数、图像和校正表的非连续行、
单目边界、重复使用、关闭 GPU 以及校正表变更回退。
带数据集参数时检查实际图像；最后一个参数控制最大采样数，
大于数据集帧数时逐帧检查全部输入。图像和参考输出只用于检查，不提交代码分支。

## 验证限制

回放没有外部真值；地图与建图线程调度会使不同运行的轨迹发生差异。
输入像素一致、有效位姿率和独立 PnP 残差是分别检查的证据。
纯双目回放不替代惯性初始化和导航融合。
已确认实际重启后服务自动启动；长期 VIO、GUI 和实飞尚未验收。
飞控观测发布与飞手授权门控保持原条件。

## 同线程取流与校正对照

Jetson Orin Nano，25W，6 核 CPU 上限 1.344 GHz，GPU 上限 918 MHz。
以下服务对照使用原 schedutil 调度策略，40 秒资源采样，完整状态内录和自动验证均开启。

| 配置 | 服务帧率中位数 | 校正中位耗时 | 六核平均 CPU 占用 | 有效导航帧 |
|---|---:|---:|---:|---:|
| CPU 校正 + CPU FAST | 13.8 fps | 19.7 ms | 64.1% | 679/679 |
| GPU 校正 + CPU FAST | 12.9 fps | 5.4 ms | 55.2% | 647/647 |
| GPU 校正 + GPU FAST | 13.2 fps | 4.9 ms | 51.3% | 652/652 |

三组静态导航均保持单一参考 epoch，正常停止后写出包数与帧数一致。
GPU 校正节约 CPU，但本轮整套服务帧率没有提升；不能把单步骤耗时下降写成整体加速。

全部 557 组真实双目输入与四组合成图的校正输出逐像素相等，差异像素为 0。
合成图包括全部 1024 种分数系数、黑白/常量/随机输入、边界和非连续行。
独立完整数据检查的 CPU/GPU 校正中位耗时为 10.02/6.44 ms。

同一段运动数据分别回放 CPU 和 GPU 校正，共 1114 帧；
两轮均为 556/557 帧有效、1 帧丢失、末帧有效，未发生完整地图重置。
独立 PnP 帧间旋转残差 P95 为 0.167°/0.244°；
该参考并非外部真值，回放的地图优化和线程调度存在运行间差异。
计算与解码在离线回放中争用同一资源，总回放吞吐为 11.06/11.04 fps，
本阶段没有证明整体吞吐提高。

|---|---:|---:|---:|---:|
| CPU | 13.5 fps | 63.2 ms | 12.7 ms | 640/640 |

## 当前服务分工

常驻纯双目服务使用 GPU 校正 + GPU FAST，CPU 负责 JPEG 灰度解码、
金字塔、方向与描述子、匹配、跟踪和地图优化。
保留每目 960×720、1000 配置特征和 CPU 金字塔层级并行。
功耗仍为 25W、CPU 最高 1.344 GHz，频率调度恢复 schedutil。

取流线程只读取并保存原始 MJPEG 字节，工作线程解码及校正，主线程跟踪。
取流返回后立即记录时间戳，原始字节在跨线程前取得独立存储。
待处理输入只保留最新一帧，图像与时间戳成对覆盖；校正后的交接仍只保留最新一对。
队列覆盖有计数，不承诺把相机每一帧都交给 SLAM；逐帧导航记录覆盖实际处理帧。
Stop 会唤醒等待线程，正常关闭先停止取流与工作线程，再排空记录器。

独立读取相机时，单缓冲 8 秒约 13.27 fps，双缓冲约 28.03 fps，
四缓冲约 28.03 fps。三组都设置 MJPEG 2720×960 @30，实际吞吐不等于声明值。
双缓冲和四缓冲测试仍有帧序间隙和异常 JPEG 头，解码失败的帧不进入 SLAM。
因此日常纯双目服务选双缓冲，配合持续取流和最新帧队列。

## 惯性时间标定保护

VIO_CAPTURE_BUFFERS 可以指定 1、2、3、4，手动运行默认 1；
ORB_SLAM3_CAPTURE_PIPELINE 可以指定 0、1，手动运行默认 0。
常驻纯双目服务显式使用 2 和 1。

启用 --imu-config 时，即使环境请求双缓冲和新流水线，程序也强制单缓冲、
关闭跨线程取流，继续使用已经标定的取流时序。
实际台架检查确认：请求 2/1，实际为 1/0；
182 帧、1523 条实际消费 IMU 的记录格式、批次数量和完整性均通过。
这项检查未完成 VIBA2，也没有重新验证 GPU 路径的曝光时间偏移。

effective_launcher.conf 记录请求值，run.log 记录实际 V4L2 缓冲数和流水线状态。
不能仅看环境变量就认定惯性入口使用了多缓冲。
[CAPTURE_STAGE] 分开记录取流等待和解码耗时；
并行各阶段会重叠，不能将这些耗时直接相加当作服务帧率。

## 双缓冲并行取流对照

以下三组均使用双缓冲、独立取流、CPU 层级并行，保持状态内录和自动验证。
每组有 9 个约 5 秒的服务窗口，以及 40 秒资源采样。

| 配置 | 服务 fps 范围 / 中位数 | 六核平均 CPU | 位姿时延中位数 | 有效导航帧 |
|---|---|---:|---:|---:|
| CPU 校正 + CPU FAST | 13.6–14.4 / 13.9 | 73.1% | 144.0 ms | 690/690 |
| GPU 校正 + CPU FAST | 13.8–14.6 / 14.1 | 59.9% | 123.5 ms | 700/700 |
| GPU 校正 + GPU FAST | 12.8–14.7 / 14.1 | 55.6% | 109.9 ms | 695/695 |

GPU 组合的校正中位耗时为 5.1 ms，GPU 采样峰值 70%。
相同双缓冲条件下，GPU 组合的主要收益是释放 CPU 和降低位姿时延；
整体帧率只有小幅变化，尚未达到 30 fps。
和此前单缓冲常驻约 13.2 fps 相比，本配置约 14.1 fps；跨轮比较会受场景和调度影响。

CPU/GPU FAST 在 960×720 下完成 4 组合成图和 20 张真实图的关键点及描述子逐字节
一致性检查，CUDA 调用计数 26；校正另有全部 557 组输入逐像素一致性检查。
最新帧队列通过 10000 帧并发测试，配对时间戳、覆盖计数、停止唤醒均通过。
12 组静态对照共 7815 帧有效导航均完整收尾，其中包含频率与线程分工实验；
未采用的频率策略没有写入服务配置。

手动复现当前纯双目分工：

~~~bash
ORB_SLAM3_RECTIFY_BACKEND=cuda ORB_SLAM3_FAST_BACKEND=cuda \
ORB_SLAM3_CAPTURE_PIPELINE=1 VIO_CAPTURE_BUFFERS=2 \
VIO_PROCESSING_PROFILE=light ORB_SLAM3_PARALLEL_LEVELS=1 \
bash run_recovery_test.sh --headless --px4-config config/decxin_px4.yaml
~~~

当前记录证明像素、特征一致性及台架静态表现，没有证明新时序在运动 VIO、
外部真值定位或实飞中无损。飞控观测发布继续关闭。

## 启动首包与异常输入

MJPEG 的首包可能为空、头部异常或解码失败。启动先检查最多 20 帧，
跳过无效帧，遇到有效且尺寸正确的灰度图后才创建 SLAM。
全部失败则明确退出，由守护进程重试；停止信号会终止等待。
运行阶段使用同样的格式和尺寸检查，不把空帧或错误尺寸交给跟踪。

回归覆盖坏首包、错误尺寸后恢复、有效 JPEG 像素不变、连续 20 帧失败和取消；
独立 CMake 构建与 CTest 已通过。

## 重启复核与 OpenCV 线程预算

实际重启后，px4-vio 和 pilot-navigation 均已自动运行，内录、原始 IMU 和导航健康
验证正常。GPU 校正、GPU FAST、960×720 / 1000 特征、双缓冲和独立取流均保持。

OpenCV 使用 TBB，单独设置 OPENCV_FOR_THREADS_NUM 在当前版本没有改变
getNumThreads 的回读值。因此提供 ORB_SLAM3_CV_THREADS 显式调用 setNumThreads，
支持 1–6；未设置时保留原默认线程数，启动日志打印实际值。
可选线程数仅通过服务重启检查，没有再执行整机重启。

以下每组连续测量 45 秒、9 个约 5 秒窗口：

| OpenCV 线程数 | 服务 fps 范围 / 中位数 | SLAM 中位耗时 | 位姿时延中位数 |

| 默认 6 | 14.0–15.0 / 14.5 | 67.2 ms | 113.4 ms |
| 显式 4 | 14.1–15.0 / 14.6 | 66.2 ms | 106.1 ms |

四线程帧率仅高约 0.7%，本轮不足以证明明确提速，默认仍为六线程。
临时覆盖已删除，常驻服务恢复默认。分辨率、特征数、GPU 分工和标定参数均未调整。

四线程下 4 组合成图与 20 张真实图的 CPU/GPU 关键点及描述子逐字节一致，
CUDA 调用计数 26；合法配置检查与非法线程数拒绝检查通过。
